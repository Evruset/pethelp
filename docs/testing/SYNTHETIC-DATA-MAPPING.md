## Fixture persistence and recovery

`synthetic_fixture.sources/raw/mapping` are local tooling tables created only after environment/DB/namespace guard; not a production migration. PUBLIC privileges revoked. No HTTP route exposes them. Raw records append-only under this importer; no overwrite on rerun. Existing native UUID without matching fixture ownership causes STOP. A global namespace advisory lock serializes seed processes. Native slot publication uses a deterministic idempotency key; if publication commits before mapping, replay returns the accepted batch and mapping resumes. No existing slot is reopened, rescheduled or stripped of holds. Metadata attachment does not change counters or accepted source service.

Initial implementation review corrections: transport keys changed to canonical doctor/actual-time keys (only fixture map rekeyed);133 UNKNOWN sterilization values corrected to null on proven initial, untouched profile-v1 fixture pets. Subsequent seeds never update Pet edits. Rolling retention keeps old booked/history slots; 35000 is the current14day window, not a lifetime total.

Product Owner selected **non-destructive fresh-DB reset**. `reset-fixture` requires exact namespace confirmation, checks source/archive ownership, creates a new guarded `synthetic_multiclinic_v4_r_<12hex>` database on the test-owned resource, applies migrations/checksums, seeds and verifies. It never purges or clones the previous DB, histories or sessions. Existing targets fail; failed new generations are retained. Activation is explicit via `SYNTHETIC_DATABASE_NAME`; no running demo or prior DB is switched automatically. No destructive reset or deletion/retention authority is claimed.

## UUID compatibility

The transport uses UUID v5, while CreateHold DTO explicitly accepts v4. Native fixture IDs deterministically replace only the version nibble (5→4), retaining a bijection for this pinned archive. `synthetic_fixture.mapping` retains the exact original UUID as external ID. Raw source bytes/fields are unchanged. This is an application-compatible fixture mapping, not a change to Booking validation. The first incompatible `synthetic_multiclinic` attempt is retained as diagnostic data, never reset/dropped; the runnable fixture uses the fresh `_v4` database.

Native shifts keep Catalog doctor identity and ClinicStaff identity distinct; fixture source maps them explicitly to the same fixture UUID. This internal fixture importer does not establish general personal veterinarian assignment. Existing Schedule read returns additive optional `doctorShifts`/`timezone`; Admin/Reception HTTP roles and current memberships remain authoritative. No new public mutation route. btree_gist provisioning is an explicit deployment requirement; populated down migration refuses loss.
