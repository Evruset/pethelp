# 00 — Полномочия, источники истины и пилотный scope

**Contract:** `VETORA-GOV-001` · `v0.1.0` · `PROPOSED_FOR_PO_APPROVAL`.

## Иерархия

1. Актуальная задача Jira и связанные с ней **нормативные** Confluence/Scope Freeze.
2. Утверждённые репозиторные domain/API/security contracts и ADR, в пределах своих ревизий.
3. Фактический код, применённые migrations, OpenAPI и выполненные тесты — для ответа «что существует».
4. `docs/ai/current-state.md` — execution/evidence overlay, не источник новых бизнес-правил.
5. V35/V07 и другие HTML/UX-прототипы — эталон presentation, **не** источник серверных состояний и прав.

Если нормативный бизнес-контракт и реализация расходятся, остановить затронутую работу, описать конфликт и альтернативы и выбрать применимый статус из [AGENTS.md](../../AGENTS.md).

## Граница первой версии

Положительное MVP-ядро: поиск проверенных клиник/услуг/врача/времени → заявка/подтверждение и статус → роль администратора (очередь, расписание, пациенты) → роль врача (свои назначенные приёмы, ограниченный результат) → уведомление/история → минимальное измерение источника и состоявшегося визита.

**PILOT_V1** — узкий профиль возможностей. Он не переключает сам по себе бизнес-режим подтверждения: тот определяется серверным профилем договора клиники (`MVP_V1_MANUAL` / `V15_AUTO_CONFIRM`). На первом пилоте по умолчанию — ручное подтверждение, пока отдельный контракт не разрешил auto.

Платежи за лечение получает клиника. Vetora не является медицинской/платёжной стороной от имени клиники только потому, что посредничает с записью. Коммерческая гипотеза CPA — 550 ₽ за **первый доказанный состоявшийся визит**; CRM — ориентир 4 990–8 990 ₽/мес., 60-дневный пробный период. Это бизнес-гипотезы, **не** разрешение внедрять автоматический billing. Не начислять CPA за время, просто прошедшее по календарю, за заявку, дубликат или no-show. Не совмещать CPA и процентную комиссию с одного визита без нового решения.

Отложенные контуры: полноценная МИС и обязательная интеграция с ней, платежи/эквайринг, телемедицина, страхование, emergency routing, Push, SMS, Telegram, AI-диагностика/предсказания, OCR-продолжение, расширенный клинический документ, сложные рейтинги/BI, маркетплейс зоотоваров/груминг, мультигород. Legacy code можно сохранить изолированным, но его наличие не делает функцию частью пилота.

## Неявные решения запрещены

- Нет backend-роли `CLINIC_MANAGER` на зафиксированном commit; роль «Руководитель» в HTML — presentation concept. Не добавлять роль и не выдавать чужие capabilities по умолчанию.
- «Врач видит только свой календарь» — целевое требование. На baseline нет доказанной персональной серверной выборки по doctor assignment. Не объявлять его выполненным по UI-фильтру.
- Нельзя считать `gh-pages` production или публичные цены/рейтинги подтверждёнными.
- Нельзя автоматически считать чеки реального пилота, UAT, юридической приемки, 152-ФЗ, security-audit и SLA исполненными на основе synthetic E2E.

## Порядок изменения норматива

Любая новая роль, статус, платный тариф, схема хранения, retention period, provider или расширение scope требует отдельного Decision Record: `decision_id`, `owner`, `sources`, `options`, `impact`, `approved_revision`, `date`, `excluded_items`. До утверждения — `PROPOSED`, `UNKNOWN` или соответствующий `BLOCKED_*`.
