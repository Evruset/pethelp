# 07 — Против выдумывания фактов, требований и нереализуемых обещаний

**Contract:** `VETORA-TRUTH-001` · `v0.1.0` · `PROPOSED_FOR_PO_APPROVAL`.

## Только доказанные утверждения

Каждая существенная строка плана/статуса получает одну из классификаций:

| Метка | Значение | Разрешено заявлять |
|---|---|---|
| `VERIFIED_CODE` | Точный путь, символ, ref и просмотренный код | «Есть реализация на этой ревизии» |
| `VERIFIED_CONTRACT` | Normative issue/ADR/DTO+revision | «Таков утверждённый контракт» |
| `OBSERVED_TEST` | Конкретный запуск, версия, среда, assertions, exit code | «Этот тест прошёл в этой среде» |
| `OBSERVED_REAL` | Действительно полученная клиническая/провайдерская/UAT запись со scoped доказательствами | «Этот реальный gate пройден» |
| `INFERRED` | Вывод из явно перечисленных фактов | «Вероятно; требуется проверка» |
| `PROPOSED` | Новая проектная гипотеза | «Вариант для согласования, не реализован» |
| `UNKNOWN` | Нет надёжного подтверждения | «Неизвестно / нет данных» |

Запрещены замены `UNKNOWN` правдоподобным результатом, несуществующие поставщики, случайные production ID, фальшивые геоточки, рейтинги, доступность, цены, статус публикации, замеры производительности, ответ клиники, сертификаты, медицинские заключения и одобрения.

## Feasibility gate до изменения кода

Для любого требования ответить в Task Brief:

1. Есть ли действующая сущность/API/harness? Если нет — нужен ли новый backend/таблица/provider/permission?
2. Есть ли все исходные данные, их owner и законное назначение? Кто подтверждает реальные данные?
3. Может ли требование быть исполнено в текущем scope, бюджете и физической среде? Нужен ли внешний API/аккаунт/устройство/клиника?
4. Что можно доказать локально, а что требует отдельной реальной приёмки?
5. Какой самый маленький жизнеспособный срез без расширения домена?

Если **нет технического или ресурсного пути** в разрешённом scope: `BLOCKED_FEASIBILITY` как локальная причина и существующий допустимый machine status `BLOCKED_PRODUCT_DECISION` / `BLOCKED_EXTERNAL_DEPENDENCY` / `BLOCKED_SCOPE_EXPANSION` / `BLOCKED_TOOLING`. Не симулировать достижимость, не начинать архитектурную переделку вместо отказа.

## Антигаллюцинационные правила интерфейса

- Кнопка обещает только тот результат, который реально выполняет обработчик и backend. Интерактивная заглушка с fake success — STOP.
- Нет server verified slot → нет текста «Свободно на 15:30» в реальном каталоге. Синтетический демонстрационный слот маркируется тестовым.
- Цена «от» требует состав/исключения и источника от клиники; равный `serviceCode` допустим только при доказуемо сопоставимом составе.
- Auth code `000000`, фиксированный телефон, `localStorage` для заявок или клинических файлов — DEMO ONLY; не подключать реальные пациентские данные.
- Клиентские роли, рейтинг и завершение по локальным часам никогда не являются backend proof.
- PO acceptance, signed build, real-device, deployed environment, real provider, pilot clinic, genuine visit и security signoff нельзя выдавать из synthetic fixtures/test doubles.

## Проработка новой идеи

Новая функция проходит `PROPOSED → DECISION_REQUIRED → APPROVED_SCOPE → IMPLEMENTABLE` только как **состояние проектного предложения**, не Jira workflow/runtime enum. На каждом шаге хранить источники, оценку зависимостей, UX/доступы, cost/risks, альтернативы и точное решение PO. Не считать громкое пожелание пользователя исполнимой задачей без DoR.
